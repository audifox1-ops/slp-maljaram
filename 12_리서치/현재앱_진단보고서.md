# SLP.Docs 현재 앱 진단 보고서

## 1. 프로젝트 개요

**프로젝트명**: SLP.Docs  
**버전**: 0.0.0  
**목적**: 언어재활사/미술치료사를 위한 전문 치료 일지 도우미  
**핵심 기능**: 학생 결제 내역 업로드 → 학생 정보 관리 → AI 기반 연간계획서/월별일지 자동 생성 → 문서 다운로드(Word, HWPX, PDF)

## 2. 기술 스택

### 프론트엔드
- **React 19** + TypeScript 5.8
- **Vite 6.2** (빌드 도구)
- **Tailwind CSS 4.1** (스타일링)
- **Motion/Framer Motion** (애니메이션)
- **Lucide React** (아이콘)

### 백엔드/데이터베이스
- **Firebase Firestore** (데이터 저장)
- **Firebase Auth** (인증 - 현재 미사용 상태)
- **Express.js** (개발 서버)

### AI/ML
- **Google Gemini API** (@google/genai 1.29)
- 모델: gemini-2.0-flash

### 문서 생성
- **docx** (Word 문서 생성)
- **JSZip** (HWPX 파일 생성)
- **html2pdf.js** (PDF 생성)
- **xlsx** (엑셀 파일 파싱)
- **papaparse** (CSV 파일 파싱)

### 배포
- **Vercel** (프론트엔드 배포)
- **Firebase** (데이터베이스)

## 4. 주요 화면과 기능

### 4.1 홈 화면 (Landing)
- HeroSection: 앱 소개 및 기능 안내
- FileUploadCard: CSV/Excel 파일 업로드
- FeatureGrid: 주요 기능 카드

### 4.2 문서 화면 (Docs)

- **DocumentPreview**: 연간계획서/월별일지 미리보기
- **ScheduleValidationPanel**: 결제 날짜와 수업 요일 검증
- **BatchGenerationModal**: 여러 달 일지 일괄 생성

### 4.3 학생 관리 화면 (Students)
- 학생 목록 카드형 표시
- 검색 기능
- 학생 추가/수정/삭제
- 자동 등록 (결제 데이터에서 추출)

## 5. 라우팅 구조

**라우팅 없음** (SPA 구조)  
`currentView` 상태로 `docs`와 `students` 뷰를 전환

## 6. 데이터 저장 방식

### Firestore 컬렉션
1. **students**: 학생 기본 정보
   - 문서 ID: 학생 이름
   - 필드: name, birthDate, school, disabilityType, treatmentArea, therapistName, schedule, observations

2. **payment_records**: 결제 내역
   - 문서 ID: 자동 생성
   - 필드: studentName, transactionDate, amount, treatmentArea, createdAt

3. **annual_plans**: 연간계획서
   - 문서 ID: `{studentName}_{year}`
   - 필드: currentLevel, longTermGoals, monthlyGoals, studentName, year, updatedAt

4. **monthly_journals**: 월별일지
   - 문서 ID: `{studentName}_{year}_{month}`
   - 필드: currentLevel, monthlyGoal, sessions, result, studentName, year, month, updatedAt

## 7. API/백엔드 구조

**프론트엔드 온리 앱**  
- AI 호출은 프론트엔드에서 직접 Gemini API 호출
- 데이터 저장은 Firebase Firestore 클라이언트 SDK 사용
- 개발 서버는 Express.js (Vite 미들웨어 모드)

## 8. 인증/권한 구조

**현재 미사용**  
- Firebase Auth 초기화만 되어 있음
- 실제 인증 로직 없음
- 모든 사용자가 동일한 Firestore 데이터에 접근

## 9. 상태관리 방식

**React 상태 + 커스텀 훅 패턴**
- `useState`: 컴포넌트 로컬 상태
- `useMemo`: 파생 데이터 계산
- `useCallback`: 메모이제이션된 핸들러
- `useEffect`: 사이드 이펙트, Firestore 실시간 구독

**주요 상태 흐름**:
```
App.tsx (상태 관리)
├── useStudents: 학생 정보 CRUD
├── usePayments: 결제 내역 저장/조회
├── useFileUpload: 파일 업로드 처리
├── useDocumentGenerator: AI 문서 생성
└── useDocumentPersistence: Firestore 저장/조회
```

## 12. 발견된 문제점 및 개선 필요 사항

### 12.1 보안 문제 (심각)
1. **Firebase API 키 하드코딩**: `firebase.ts:13-18`에 API 키가 하드코딩됨
2. **인증 없음**: 모든 사용자가 동일한 데이터에 접근 가능
3. **Firestore 규칙 미설정**: `firestore.rules` 파일 존재하지만 검증 필요

### 12.2 타입 안정성
1. `types.ts:67`의 `[key: string]: any` 인덱스 시그니처로 인한 타입 안정성 저하
2. `useStudents.ts:35`의 `as StudentInfo` 캐스팅
3. `aiService.ts`에서 `response.text` 타입 검증 부족

### 12.3 에러 핸들링
1. `aiService.ts:83`의 API 키 누락 시 `throw new Error('API_KEY_MISSING')` 패턴이 여러 곳에서 반복
2. `useDocumentGenerator.ts:101-109`에서 AI 에러 시 Mock 데이터로 폴백하는 로직이 복잡
3. Firebase 에러 시 `handleFirestoreError`가 에러를 다시 throw하여 호출부에서 처리 필요

### 12.4 코드 품질
1. **중복 코드**: 
   - `wordExportService.ts`의 `renderMultiline`, `createBorder` 함수 중복
   - `useDocumentGenerator.ts`에서 Mock 데이터 생성 로직 중복
2. **긴 함수**: 
   - `aiService.ts`의 프롬프트 문자열이 매우 길고 유지보수 어려움
   - `wordExportService.ts`의 테이블 생성 코드가 반복적
3. **하드코딩**: 
   - 모델명 `"gemini-2.0-flash"`가 여러 곳에서 하드코딩
   - 타임아웃 `30000ms` 하드코딩

### 12.5 성능
1. **무거운 번들**: `docx`, `xlsx`, `JSZip` 등 무거운 라이브러리가 동적 임포트 되지 않음
2. **메모이제이션 부족**: 
   - `filteredStudents` 계산이 매 렌더링 시 수행될 수 있음
   - `paymentDatesByStudent` 계산이 불필요하게 반복될 수 있음
3. **Firestore 실시간 구독**: 학생 수가 많아지면 성능 저하 가능

### 12.6 UX 문제
1. **빈 화면 처리**: 데이터가 없을 때 안내 메시지만 표시되고, 다음 단계로의 이동이 명확하지 않음
2. **로딩 상태**: AI 생성 시 긴 로딩 시간 동안 사용자 피드백 부족
3. **모바일 대응**: 일부 컴포넌트에서 모바일 레이아웃 최적화 부족
4. **인쇄 기능**: 팝업 방식의 인쇄가 번거로움

### 12.7 테스트 부재
1. 단위 테스트 없음
2. 컴포넌트 테스트 없음
3. E2E 테스트 없음
4. 린트 설정 없음 (ESLint)

### 12.8 문서화 부족
1. 컴포넌트 Props 문서화 부족
2. API 문서 없음
3. 개발 가이드 없음

## 13. 긍정적인 측면

1. **우수한 컴포넌트 분리**: 기능별로 잘 분리되어 있음
2. **커스텀 훅 패턴**: 비즈니스 로직과 UI가 잘 분리됨
3. **Firestore 실시간 동기화**: 데이터 변경 시 자동 반영
4. **AI 폴백 메커니즘**: API 키 없거나 실패 시 Mock 데이터로 동작
5. **파일 파싱 유연성**: 다양한 날짜 형식과 컬럼명 지원
6. **TypeScript 사용**: 타입 안정성 추구 (일부 제외)
7. **Tailwind CSS**: 일관된 스타일 시스템

## 15. 결론

SLP.Docs는 언어재활사/미술치료사를 위한 치료 일지 자동 생성 도구로, 핵심 기능은 구현되어 있으나 **보안, 테스트, UX 개선**이 필요한 상태입니다. 특히 인증 시스템 부재와 API 키 하드코딩은 심각한 보안 문제이며, 테스트 프레임워크 미설정은 코드 품질 관리에 어려움을 줍니다.

**최우선 개선 사항**:
1. 인증 시스템 구현 (또는 API 키 보호)
2. 테스트 프레임워크 설정 및 핵심 기능 테스트
3. UX 개선 (빈 화면, 로딩 상태, 모바일 대응)
4. 타입 안전성 강화
5. 코드 중복 제거
